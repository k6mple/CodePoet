## 1. 端点

| 方法 | 路径 | 成功 | 主要失败 |
| --- | --- | --- | --- |
| POST | `/api/v1/sandbox-runs` | 202 + `SandboxRun(status=queued)` | 401 未登录 / 403 CSRF / 404 base 不是本人 / 422 源码超限 / 429 配额满 / 503 环境不可用 |
| GET | `/api/v1/sandbox-runs/{id}` | 200 | 401 / 404（含「不是你的」） |
| GET | `/api/v1/admin/policies` | 200 | 401 / 403 |
| PATCH | `/api/v1/admin/policies` | 200 | 401 / 403 / 409 `REVISION_CONFLICT` / 422 `POLICY_FIELD_READ_ONLY` |

字段形状严格对齐 `docs/openapi.json` 的 `SandboxCreate` / `SandboxRun` / `Policies` / `PolicyUpdate`，
增量只有细则允许的 `policySnapshot`、`metrics.peakMemoryMiB`、`auditFindings`、`Policies.auditRules`。

`SandboxRun` **不返回源码**，只给 `sourceHash`。源码在库里随归属授权读取。

**base 授权是 ownership，不是「可读」**。OpenAPI 的 `POST /sandbox-runs` 写的是
「基础 generation 必须本人拥有」；用 `can_read` 会多放开两条路：管理员能拿别人的
快照跑 DSL，任何人能拿公开作品的快照当 base。后者尤其糟——产出的 fragment 归我，
来源链却写成「我改了别人的图」，而原作者的授权范围里没有这一项。

### `sandbox_runs`

`id / owner_id / base_generation_id / status / policy_revision / policy_snapshot_json /
source_hash / source_json / generation_id / metrics_json / error_json /
audit_findings_json / request_id / created_at / started_at / finished_at`

三条库级约束不是装饰：

```sql
CHECK (status IN ('queued','running','succeeded','failed','timed_out','cancelled'))
-- succeeded 必须有产物，非 succeeded 必须没有
CHECK ((status =  'succeeded' AND generation_id IS NOT NULL) OR
       (status <> 'succeeded' AND generation_id IS NULL))
-- 终态必须有结束时间，未终结的不许提前填
CHECK ((status IN ('queued','running') AND finished_at IS NULL) OR
       (status IN ('succeeded','failed','timed_out','cancelled') AND finished_at IS NOT NULL))
```

### `policies`（单行，`id = 1`）

`revision` 做乐观锁，`values_json` 存当前值，`updated_by` 记最后修改人。
**硬上限不存库**——它是代码常量（`services/policy.py` 的 `HARD_LIMITS`），
因为「不可突破的界」不该是能被写坏的数据。

初始行由迁移插入；`test_policy.DefaultsTests` 会读库与 `DEFAULT_VALUES` 逐字段比对，
防止「新库用迁移那份、兜底创建用代码那份」两套值漂移。

## 3. 隔离执行

```
API 进程                          worker 子进程（python -B -m app.engine.dsl_worker）
  create_run   → 202 + queued
  executor.submit(run_id)
    ├─ 原子 UPDATE queued→running
    ├─ 组 payload（base IR / 策略快照 / 模板上下文）
    └─ stdin 有界 JSON  ────────→  compile_program（静态审计）
                                  dsl.run（追加图元）
                      ←────────  stdout 有界 JSON
    ├─ 父进程校验 IR（DrawingIR + validate_ir）
    └─ 同一事务写 generation + run 终态
```

* **worker 不持有数据库、不持有密钥**：`_worker_env()` 只传 `SYSTEMROOT` / `PATH` /
  `TEMP` 这类运行必需项，`CODEPOET_*`（数据库路径、知识图谱凭据）一律不下传。
* **不把 Session 传进线程**：执行线程自己开 `Session`、自己提交、自己关闭。
* **静态拒绝也留 run**：AST 违规照样有 `sandbox_runs` 行，`status=failed`、
  `error.code=DSL_AUDIT_REJECTED`、`generation_id=NULL`，同时写一条 `auditFindings`。
* **请求格式错误不建 run**：源码超 16KiB、JSON 坏在 Pydantic 层就被拒（422），
  那不是「一次被拒的执行」，是「一个没发出来的请求」。
* **源码不进 provenance**：`Provenance` 只留 `fragmentSourceHash`，`fragmentSource`
  恒为 null。provenance 会随 `GET /generations/{id}` 返回，作品发布后
  `GET /work-versions/{id}` 是匿名可读的——把源码写进去等于作品公开的一刻源码也公开。
  溯源走 `sourceHash → sandbox_runs`，权限由 run 的归属决定。

## 4. 并发

两处「先数/先比，再写」都必须是原子的，否则单线程测试全绿、并发时失效。

| 位置 | 机制 | 失效后果 |
| --- | --- | --- |
| 配额（每用户 2 个未完成 run） | `services.locking.begin_immediate` 独占写事务包住 COUNT + INSERT | 并发提交能突破上限 |
| 策略乐观锁 | `UPDATE ... WHERE id=1 AND revision=expectedRevision`，`rowcount!=1` → 409 | 并发 PATCH 后写覆盖先写，客户端拿不到 409 |

两处都不是靠「Python 里先比较一下」：SQLite 的 DEFERRED 事务里读不加锁，
读与写之间有窗口；条件必须在 UPDATE 的 WHERE 里，或事务一开始就拿写锁。

`services/locking.py` 是新抽出来的公共模块，`services/works.py` 里原来那份
`_begin_immediate` 已改为调用它——同一机制两处各写一遍迟早会漂，而这里漂移的
后果是限流失效，不是报错。

## 5. 预算与退出码

| 维度 | 默认 | 判据 | 终态 |
| --- | --- | --- | --- |
| wall | 2000ms | worker 看门狗（不含启动开销） | `timed_out` + `DSL_TIMEOUT` |
| CPU | 1s | worker 看门狗 | `failed` + `DSL_CPU_LIMIT` |
| 内存 | 256MiB | worker 看门狗 + Job Object 内核兜底 | `failed` + `DSL_MEMORY_LIMIT` |
| 绘图调用 | 1000 | 解释器内计数 | `failed` + `DSL_CALL_LIMIT` |
| 解释步数 | 10000（v1 写死） | 解释器内计数 | `failed` + `DSL_STEP_LIMIT` |
| AST 节点 | 2000 | 编译期 | `failed` + `DSL_AUDIT_REJECTED` |

worker 退出码：`70` CPU / `71` 内存 / `72` 协议错误 / `73` wall。
Windows 下如果被 Job Object 的内存上限干掉，退出码是 `0xC0000017`
（`STATUS_NO_MEMORY`，无符号 3221225773），与 `71` 统一由 `is_memory_exit()` 认。

Job Object 的内存上限有 **64MiB 下限**：再低连 Python 都加载不完 DLL，
进程会死在 `0xC0000142`，worker 的看门狗根本没机会运行。细粒度判定由看门狗负责，
内核那层只是防止「看门狗来不及」的兜底。

**父进程的 wall 兜底** = `dslWallTimeMs` + 2s（启动允许）+ 0.5s（余量）。
放这么宽是因为策略值只约束「解释多久」，不该把 Python 启动的 300ms 算进去。

## 6. 策略

可写（本期）：`dslWallTimeMs`、`dslCpuTimeSeconds`、`dslMemoryMiB`、
`dslMaxDrawCalls`、`dslMaxAstNodes`、`dslMaxRangeIterations`、`enabledDslFunctions`。

只读（提交不同值 → 422 `POLICY_FIELD_READ_ONLY`）：其余 9 项。

硬上限（`HARD_LIMITS`，只能收紧不能放松）：

| 字段 | 硬上限 | 来源 |
| --- | --- | --- |
| maxIRNodes | 200 | `engine/sample.py` 的 `MAX_NODES` |
| maxVertices | 2000 | `engine/validate.py` 的 `MAX_TOTAL_VERTICES` |
| maxRequestBytes | 262144 | `main.py` 的 256KiB 请求上限 |
| maxIRBytes | 262144 | core-demo 无独立 IR 字节上限，取与请求体一致 |
| maxParameters | 16 | `Capabilities.maxParameters` |
| dslWallTimeMs / dslCpuTimeSeconds / dslMemoryMiB | 2000 / 1 / 256 | 细则第 7 节默认值 |
| dslMaxDrawCalls | 1000 | 同上「1000 calls」 |
| dslMaxAstNodes | 2000 | 契约 dslMaxAstNodes 上界 |
| dslMaxRangeIterations | 1 | DSL v1 没有循环 |

**快照绑定**：`sandbox_runs.policy_snapshot_json` 在受理时冻结。之后 PATCH 只影响新提交的
run，已在跑的用旧值——有专门用例（`test_run_keeps_policy_snapshot_taken_at_submission`）
先建 run、再收紧策略、再执行，断言它仍按旧快照跑完。

`auditRules` 固定 6 条，全部 `enabled=true`，没有写入口。

### #25（S1-A1 解释器）

| 级别 | 问题 | 修法 |

### #26（S1-A2 沙箱与策略）

| 级别 | 问题 | 修法 |
| --- | --- | --- |
| P2 | 策略乐观锁只在 Python 里比 revision，UPDATE 的 WHERE 没带条件 | 条件进 WHERE，`rowcount != 1` → 409；提交后 `expire_all()` 防读回陈旧值 |
| P2 | 配额 COUNT 与 INSERT 不在同一事务 | `services/locking.begin_immediate` 包住两步；`probe()` 移到拿锁之前，避免把子进程自检包进写事务 |
| P2 | base 用 `can_read`，与 OpenAPI 的「必须本人拥有」不一致 | 收紧为 `base.owner_id == user.id`；补管理员场景用例 |
| P2 | 源码经 `Provenance.fragmentSource` 暴露给公开读者 | provenance 只留 hash；补「公开详情不含源码」用例 |
| P3 | `auditFindings` 的 `ruleId` 用错误码、`line/column` 恒 0 | 规则 ID 常量定义在 `engine/dsl.py`，策略清单引用同一批；位置优先用 JSON 解析的真实行列，其次用 ops 下标换算 |

### 一个副产物

`RULE_BASE_UNMODIFIED` 原先只写在清单里、没有对应检查——「声明了但没实现」。
现在 `dsl.run()` 在组装结果前逐节点比对 base 与结果的副本，真被改了就报这条规则。
清单里的每条规则都能对上一条真实的拒绝路径。

### 反向验证从 7 条扩到 11 条

新增：base ownership、独占写事务、乐观锁 WHERE 条件、源码不出 provenance。
乐观锁那条第一次写错了——走 HTTP 时 PATCH 用的是新 Session，`db.get` 直接读到
新 revision，退化掉 WHERE 条件测试照样通过。改成复用同一个 Session 的过期
identity map 之后才真正能区分。
