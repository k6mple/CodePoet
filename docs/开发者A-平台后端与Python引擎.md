## 3. 第一包 S0 的具体修改检查

1. 对照真实路由/Pydantic和现有OpenAPI；当前请求中canvas2d、browser_upload和Literal[False]均是硬约束，仅改枚举展示不够。
2. 分步扩充GenerationCreate、模板创建/编辑、会话state、能力声明和服务校验；新模板能力只能通过新版本审核，不改旧发布快照。
3. RenderCreate使用模式判别，server任务不接受clientEnvironment/上传帧；dispatcher固定入口；沿用既有作业查询/取消/作品绑定。
4. rendererVersion独立于语义ENGINE_VERSION；旧Canvas版本不能因重构随意递增。复现从旧backend推导执行模式，禁止默认为Canvas。
5. 同步shared schema与两个OpenAPI相应部分；保持core-demo限额。B拿到真实成功/失败JSON后再接接口。

S0第一天先交浏览器后端分支；server实现并入R3预算，不为等Turtle阻断CSS/WebGL。已保存Canvas作品仍须真实重开/复现。

R1（CSS）与R2（WebGL）由B主责；A的接口支持计入S0，按B的真实渲染验收结果启用各自capability与模板新版本支持集合，不能在适配器未完成时提前宣告可保存。超出S0预算的联调计入实际缓冲，及时更新看板。

## 4. Q1、S1、R3 的关键风险

质量：AABB不能作为所有交叠的最终判断，莲瓣设计重叠要有排除依据；无语义色板写not_applicable；SNR要有期望mask和真实PNG对照。报告阈值固定并版本化，失败写unavailable而非生成艺术高分。

受限执行：不执行任意Python。DSL生成IR仍需现行IR/参数校验，不突破节点上限。AST规则固定、启用函数/限额可配置；CPU/内存必须目标OS真实执行限制，不用预校验拒绝代替资源熔断测试。超时杀进程组且下一任务可成功；捕获内存耗尽不能拖垮API进程。

Turtle：先证明目标环境能稳定导出再写适配器；几何必须由Turtle产生，Pillow只合成转换。标准透明/裁剪和三时刻不支持时明确收缩能力；无法可靠保存/复现则available=false。桌面交互窗口不是服务器交付方案。

## 6. agent任务写法与验收

给agent的第一项可直接使用：

```text
任务S0-A：在CodePoet当前基线扩展浏览器渲染后端请求契约。
先读根/目标AGENTS、总纲、提分阶段接口增量约定和当前请求/服务代码。
只改backend、shared/schemas和接口/OpenAPI文档，不改frontend。
将template/semantic/ir请求、模板版本写入的backend限制改为能力驱动；旧Canvas请求无新必填字段。
先接CSS/browser_upload，不提前宣称Turtle/server已实现；保留200节点等core-demo限制。
实际验证旧Canvas链、不可用backend拒绝、模板supportedBackends拒绝和新CSS请求样例。
报告真实修改/命令/结果/未完成项；达到预算即给出已完成切片与阻塞，不自动push。
```

后续一次只给Q1、S1或R3中的一个切片，附输入/失败条件/预算。不要同时让agent实现完整OpenAPI。先审安全/权限/不可变版本等核心差异，再跑有意义的边界测试；每新增持久化字段要证明旧库迁移、旧记录读取和回退行为。

验收分层：算法/解释器单测 → 真HTTP → 与B的真实浏览器作品链 → 目标环境。最终记录启动环境、依赖、命令、退出码、实际产物、已知缺口；无新功能测试不能复用311/40声称全过。
