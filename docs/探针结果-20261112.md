## 探针一：Tk / Turtle → PNG

| 步骤 | 结果 |
| --- | --- |
| `tkinter` 导入 + 离屏画布（`Tk().withdraw()` + `Canvas`） | **通过**，用 `RawTurtle` 真画了圆 + 直线 |
| `canvas.postscript()` 导出 EPS | **通过**，8479 字节，52ms，头 `%!PS-Adobe-3.0 EPSF-3.0` |
| EPS → PNG 栅格化 | **失败** |

失败原因是缺 **Ghostscript**：

```
Ghostscript: 未安装（gswin64c / gswin32c / gs 都不在 PATH）
Pillow 直接打开 EPS：OSError: Unable to locate Ghostscript on paths
```

**关键事实**：`canvas.postscript()` 是 Tk 画布唯一可导出的中间格式，而它的下游（含 Pillow 的 EPS 解码器）**都依赖 Ghostscript**。没有 GS，EPS 就是一份无法进管线的死文件。

### 判定：R3 的 Turtle 路径本机不可行 → 延期，8h 预算转 Q1/集成

按细则「先证明目标环境能稳定导出再写适配器」「无法可靠保存/复现则延期」，不在本机凑环境。

要点：**几何必须由 Turtle 产生、Pillow 只做合成转换**，用 Pillow 直接画整图属于文档明令禁止的「伪称 Turtle」，不作为备选。

若后续仍要做，需要补两件（本机都没有）：

1. 安装 Ghostscript（`gswin64c`），并确认比赛部署环境允许装；
2. 目标机同样的 Tk 版本 + 字体 + 权限——本机装上不等于比赛机可部署。

## 探针二：Windows 隔离限制

用 ctypes 直接挂 **Job Object**，不依赖 psutil，也不靠「预检拒绝」冒充资源熔断。

### 判据为什么改了一版

初版判据是「退出码非零 + 耗时比预期短」。**这个判据分不清三件事**：资源超限被杀、普通异常退出、外部终止——三者都是「非零 + 短」。评审用一次普通异常退出（退出码 1、0.24s）就复现了误判。

### 第二版判据（评审后又改了一次）

第二版写成「两条独立证据，任一成立即判定」——内核通知 **或** 行为特征（提前退出 +
分配块数少于对照）。评审指出这留了后门：**无通知时行为特征照样能把普通异常退出
判成熔断**；CPU 分支更弱，连退出码都没看，而且对照组用 3s、实验组用 12s，
两个负载长度不同，比时长本身没有意义。

第三版改成：**判定只认内核 Job 通知**。

| 证据 | 作用 |
| --- | --- |
| 内核通知 `PROCESS_MEMORY_LIMIT` / `END_OF_PROCESS_TIME` | **唯一判定依据** |
| 同负载无约束对照组（时长完全一致） | 排除「这个负载自己就会退出」 |
| 进度块数 / 耗时 | **仅作旁证写进报告，不参与判定** |

拿不到通知时，即使行为看起来像熔断，也标 **「未能判定」**——不拿行为反推原因。
代价是某些环境取不到 Job 通知就只能说「没证据」，这个代价是刻意的。

### 实测结果（本机重跑）

| 场景 | 对照组（无约束） | 实验组（限额） | 内核通知 |
| --- | --- | --- | --- |
| 内存 240MiB 负载，限额 80MiB | 分配 **60/60** 块，跑完，0.33s，退出码 0 | 分配 **17/60** 块（28%），0.27s，退出码 1 | **`PROCESS_MEMORY_LIMIT`** |
| CPU 12s 负载（对照与实验同长），限额 0.5s CPU | 正常跑完 **12.27s**，退出码 0 | **2.18s** 退出（本应 12s），退出码 **0xC0000044** | **`END_OF_PROCESS_TIME`** |

`0xC0000044` 就是 `STATUS_QUOTA_EXCEEDED`——这是内核自己的语义，不是推测。

**这里正好复现了评审的反例**：内存组的退出码确实是 `1`、耗时确实只有 0.28s，与「普通异常退出」在数值上完全无法区分（进程内部是 `MemoryError` 冒泡出来的）。现在区分开它的是**内核的 `PROCESS_MEMORY_LIMIT` 通知**——行为数据（17/60 块）只是旁证。

**反向验证**：把 `limit_hits()` 改成恒返回空列表（模拟「本环境取不到 Job 通知」），
两个分支都变成：

```
→ **未能判定**：行为上像被限额拦住，但没收到内核通知，不排除普通异常退出。
总判定：隔离限制不完整：内存限额：无内核通知，未能判定、CPU 限额：无内核通知，未能判定
```

即「行为像」不再能单独得出结论。这正是评审要求的行为。

### 进程树：`kill()` 不够，`TerminateJobObject` 才够

| 做法 | 结果 |
| --- | --- |
| 墙钟超时后只 `proc.kill()` | **父进程死，孙进程残留**（pid 仍存活） |
| `TerminateJobObject(job, 1)` | **整体回收：活跃进程 5 → 0，子进程不再存活** |
| 熔断之后起新任务 | 正常，退出码 0（状态不粘） |

### 判定：S1 可以按计划做，但有一条硬约束

Job Object 的内存/CPU 限额在目标机上**真的生效**，不是只有文档承诺。

> **`Popen.kill()` 只杀直接子进程，孙进程会残留。** worker 必须用 `TerminateJobObject` 一次性终止整个作业，并在结束后**校验活跃进程数为 0**（`QueryInformationJobObject` 的 `ActiveProcesses`）。否则一个超时任务会一直挂着和下一个任务抢资源。

这条直接写进 S1-A2 的实现要求。

### 本探针的验证边界

- 只说「本机验证通过」，不推断目标比赛环境；
- **并发配额未测**（多 worker 同时跑时的总内存/总 CPU）、磁盘写满未测 —— 留到 S1-A2；
- 违规信息类（`JobObjectLimitViolationInformation`）在本机未取到有效值，退出原因以 Job 通知为准，不以它为依据；
- S1 生产 worker 还需要的额外验证（墙钟限制、配额分配、多并发下的公平性）不在本探针范围内，单独验证。

# 补测：知识图谱来源（2026-11-13，G-RESOURCE 门槛的另一半）

> 11/12 晚测 Wikidata 两个端点全部连不上、DBpedia 同一 URL 一次 200 一次 000，
> 当时判定「来源不可用」。11/13 上午网络恢复后重测，结论反转。
> 脚本：`scripts/probe_kg.py`（只读公开接口、不带凭据、不写任何数据）。

## 来源可达性

| 端点 | 结果 |
| --- | --- |
| `www.wikidata.org/w/api.php`（搜索） | **200** |
| `query.wikidata.org/sparql`（查询） | **200**，但**随即 429 限流** |
| `dbpedia.org/data/*` | 000，仍不可用 |

SPARQL 的限流原文：

```
HTTP 429: Aggressively rate-limiting to 1 req / min - this rule was created during active wdqs outage (797a132)
```

即 Wikidata Query Service 正在故障期，每分钟只放 1 次。**这不能当依赖。**

## 关键发现：不用 SPARQL 也能拿到一跳关系

Wikidata 的 `claims` 里，`datavalue.type == "wikibase-entityid"` 的那些属性本身就是
指向其他实体的关系。用 `Special:EntityData/{Q}.json` 一次取回实体，再按白名单属性
解析即可，**完全绕开限流的查询服务**。

按白名单（学名 P225 / 分类单元 P105 / 亲本 P171 / 实例于 P31 / 子类 P279 /
图片 P18 / 模式种 P1034 / 用途 P366 / 记载于 P1343 …）实测：

| 意象 | Q-id | claims | 一跳关系 | 字符串事实 | 耗时 |
| --- | --- | --- | --- | --- | --- |
| 莲 | `Q16528` | 105 | **10** | 6（学名 `Nelumbo nucifera`、图片 ×4） | 6.0s |
| 竹 | `Q670887`（竹亚科） | 67 | **17** | 5（学名 `Bambusoideae`） | 5.3s |
| 梅 | `Q157763` | 70 | **9** | 3（学名 `Prunus mume`） | 3.4s |

关系示例：`莲 --分类单元--> 植物(Q7432)`、`竹 --子类--> Q11992872`、
`梅 --亲本--> Q190545`。

## 判定：K1 可以做

验收门槛是「3 实体 2 关系端到端」，实测是 **3 实体 × 9~17 关系**，且三个意象
（莲/竹/梅）正是本项目知识库里的对象，映射链路成立。

实现约束（写进 K1-A 设计）：

1. **固定属性白名单**，不做全量抓取——105 个 claims 里大部分和视觉决策无关，
   有界读取也是细则要求；
2. **超时设 8~10s**，实测单次 3~6s，慢但可用；
3. **不依赖 SPARQL**：查询服务处于故障限流期，只作为可选增强；
4. 单实体 10 条关系就够触发「关系参与视觉决策」，不需要扩到二跳。
