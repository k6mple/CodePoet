## BE-G0-001：新建上传任务的状态与当前契约不一致

- 日期：2026-11-09。
- 状态：待后端处理；阻断 G0 全页面保存链路。
- 环境：前端 `http://127.0.0.1:13100`，同源代理到后端 `http://127.0.0.1:18100`；数据目录为 `.tools/g0-20261109-01/data/`。
- 契约：`接口文档.md` 第 7.1 节要求 browser_upload 创建后为 `running / awaiting_frames`，`expiresAt` 为五分钟后。
- 实际：`POST /api/v1/render-jobs` 返回 HTTP 202，但对象为 `queued / awaiting_frames`，`expiresAt=null`。随后 GET 同一任务仍为 queued，没有自动推进。
- 前端行为：`frontend/src/api/render.ts` 的 `uploadRenderFrames` 只允许 `running / awaiting_frames` 上传；页面展示“任务不可上传：queued”，保留任务 ID，不发送 frames，也不显示保存成功。当前行为符合约定。
- 只读定位：`backend/app/services/works.py` 的 `create_render_job` 显式写入 `status="queued"`、`expires_at=None`；`get_render_job` 只返回记录。此处未修改。

1. 在隔离库运行已有迁移和种子，启动前后端；注册并登录普通创作者。

后端按当前契约返回 `running / awaiting_frames` 与有效到期时间，并补充覆盖实际状态/字段的回归。若后端认为契约应调整，请先明确协议决定，前端再按确认结果配合；本轮未放宽校验或修改状态来绕过。

后端修复后，运行不带 `--diagnostic-upload` 的浏览器脚本，确认浏览器按钮自行完成 PNG 上传、作品保存、刷新重开和两账号隔离，`g0Passed=true` 才算 G0 通过。

到期行为、超过未完成任务数限制、帧上传断网后的页面重试仍待状态问题解决后验证；本轮没有等待五分钟来判断实际过期清理行为。
